# Подписи к идентификаторам внутри diff журнала аудита — дизайн

Дата: 2026-07-29
Статус: утверждён, готов к планированию реализации

## Задача

В развёрнутой записи журнала поля-ссылки показываются голыми идентификаторами:

```
role_id    9b75ebfc-141b-448e-ad63-97fe7ca6fa47
```

Прочитать по такой строке, что именно изменилось, невозможно. Нужны читаемые
подписи: какая роль, чей логин, какая модель.

## Что уже есть (переписывать не нужно)

Обогащение записей сделано в PR #10 и работает — но **на уровне записи**, а не
внутри снимков:

| Поле записи | Кем разрешается | Файл |
| --- | --- | --- |
| `actorLogin`, `companyLogin` | auth, `ResolveUserLogins` | `gateway/internal/service/audit_labels.go` |
| `territorySlug` | catalog, `ResolveTerritorySlugs` | там же |
| `entityLabel` | БД, колонка из спецификации триггера | миграция audit `00002` |

`labelAuditEntries` уже задаёт весь нужный нам стиль работы: пакетно на
страницу, а не на запись; ошибка резолва логируется и глотается; нерезолвнутое
значение деградирует до id. Новый код обязан следовать этому же контракту.

Снимки `old_row` / `new_row` при этом идут насквозь сырым JSON — и весь diff
рисуется из них в браузере (`frontend/src/audit/domain/diff.ts`). Отсюда голые
идентификаторы.

## Инвентарь непрозрачных полей

| Сущность (таблица) | Поля-ссылки | Тип | Владелец |
| --- | --- | --- | --- |
| `user_role` (`user_roles`) | `user_id`, `role_id` | uuid | auth |
| `role_permission` (`role_permissions`) | `role_id`, `permission_id` | uuid | auth |
| `territory_assignment` | `territory_id`, `admin_user_id` | bigint, uuid | catalog, auth |
| `placement` | `territory_id`, `model_id`, `visible_panorama_ids[]` | bigint | catalog |
| `panorama` | `territory_id` | bigint | catalog |
| `document` (`territory_documents`) | `territory_id` | bigint | catalog |

`territories`, `models` и `users` собственных ссылок в снимках не несут —
колонок вида `created_by` у них нет.

Хуже всего связующие таблицы: в спецификации триггера у `user_roles`,
`role_permissions` и `territory_assignments` колонки id и label пустые, поэтому
у записи нет даже `entityLabel`. Весь её смысл — в двух идентификаторах, и оба
нечитаемы. Это и есть случай из задачи.

## Решение

### Словарь `refs` на странице

`AuditPage` получает дополнительное поле. Снимки остаются сырыми и нетронутыми
— гейтвей по-прежнему не обязан ни с кем договариваться о форме строки.

```jsonc
{
  "entries": [ /* без изменений */ ],
  "nextCursor": 4812,
  "refs": {
    "role_id:9b75ebfc-141b-448e-ad63-97fe7ca6fa47": "Редактор",
    "user_id:3f01a2c8-…":                          "ivan.petrov",
    "model_id:7":                                   "pump-01",
    "model_id:4":                                   "crane-04"
  }
}
```

Поле необязательное и аддитивное: старый клиент его игнорирует, новый переживает
его отсутствие.

### Почему ключ — значение, а не имя поля

У изменённого поля (`role_id` с роли A на роль B) подпись нужна **обоим**
значениям. Словарь вида `{поле: подпись}` этого выразить не может в принципе,
поэтому ключуется значение.

### Почему в ключе нет вида сущности

Имена полей у нас глобально однозначны: `role_id` — всегда роль,
`admin_user_id` — всегда пользователь, `visible_panorama_ids` — всегда
панорамы. Ни одно имя не означает двух разных видов, поэтому пары
`поле:значение` достаточно и коллизий между видами не возникает — при том что
голое значение их бы дало (модель 7 и панорама 7 дали бы один ключ `7`).

Выигрыш в том, что клиенту не нужна таблица «поле → вид»: он склеивает ключ из
имени поля и значения и больше ничего не знает. Таблица остаётся на
сервере в одном экземпляре. Дублировать её на клиент нельзя — это ровно та
ловушка, что описана в `CLAUDE.md` про `frontend/src/audit/domain/vocabulary.ts`:
там список сущностей продублирован, разъехался с триггерами и молча жил дальше,
потому что тест закреплял список за самим собой.

Цена: если когда-нибудь появится таблица, где, скажем, `user_id` означает не
пользователя auth, ключи столкнутся. Замечено это будет там же, где и вносится —
в серверной таблице полей; в комментарии к ней это условие зафиксировано.

Словарь общий на страницу, а не на запись: один и тот же `role_id` повторяется
в странице десятками.

### Таблица полей (сервер)

```go
// entity → column → kind
"user_role":            {"user_id": kindUser, "role_id": kindRole},
"role_permission":      {"role_id": kindRole, "permission_id": kindPermission},
"territory_assignment": {"territory_id": kindTerritory, "admin_user_id": kindUser},
"placement":            {"territory_id": kindTerritory, "model_id": kindModel,
                         "visible_panorama_ids": kindPanorama},
"panorama":             {"territory_id": kindTerritory},
"document":             {"territory_id": kindTerritory},
```

Сущность проверяется до разбора JSON — как уже сделано в `territoryIDOf`:
страница пользовательских событий не должна платить за декодирование снимков,
в которых ссылок нет.

`visible_panorama_ids` — массив; из него собираются все элементы.

### Откуда берутся подписи

| Вид | Источник | Что подпись | Новое? |
| --- | --- | --- | --- |
| user | `ResolveUserLogins` | логин | есть |
| role | `ListRoles` | `title`, при пустом — `slug` | есть |
| permission | `ListPermissions` | `slug` (`audit:read`) | есть |
| territory / model / panorama | `ResolveLabels(kind, ids)` | `slug` | **новый RPC catalog** |

`ListRoles` и `ListPermissions` на gRPC-уровне auth не загорожены — RBAC делает
gateway, — поэтому auth-сторона обходится без правок proto. Обе таблицы
крошечные и фиксированные, тянутся целиком и только если такой идентификатор на
странице вообще встретился.

Новый RPC в catalog — один на все три вида:

```proto
rpc ResolveLabels(ResolveLabelsRequest) returns (ResolveLabelsResponse);

message LabelRef { string kind = 1; int64 id = 2; }  // territory | model | panorama
message ResolveLabelsRequest  { repeated LabelRef refs = 1; }
message ResolveLabelsResponse { map<string, string> labels = 1; }  // "model:7" → "pump-01"
```

Внутри — switch по виду и три запроса `SELECT id, slug WHERE id = ANY($1)`.
Существующий `ResolveTerritorySlugs` остаётся: его зовёт работающий
entry-level enrichment, и снос рабочего метода ради красоты потребовал бы
двухшаговой выкатки.

### Резолв в gateway

Новая функция `resolveRowRefs` рядом с `labelAuditEntries`, тот же контракт:

- пакетно на страницу, никогда не на запись;
- вызовы к auth и catalog параллельно через `errgroup` — как в scene bundle;
- ошибка резолва логируется и глотается, словарь остаётся частичным;
- нерезолвнутое значение не попадает в словарь и деградирует до голого id.

Читаемость — удобство; кто, что и когда сделал — существо, и оно в записи уже
есть. Журнал, отвечающий 500 из-за перезапуска auth, хуже журнала с uuid.

### Инвариант безопасности

Резолвится только тот идентификатор, который уже лежит в снимке, отданном этому
же читателю. Подпись называет id, который он и так держит в руках, и не
открывает ничего сверх того. Область журнала по-прежнему выводится из сессии в
`audit_scope.go` и никогда из параметра запроса.

### Путь CSV

`ListAudit` общий для JSON и CSV, поэтому получает флаг `wantRefs`. Экспорт
передаёт `false`: снимков в CSV нет (11 колонок, `old_row` / `new_row` среди них
отсутствуют), а страницы он вычитывает подряд по 200 — иначе оплачивал бы
словарь на каждой и выбрасывал.

### Фронтенд

- `AuditPage` в `audit-gateway.ts` получает `refs`; `useAuditLog` сливает
  словари страниц в один (`Object.assign`).
- Чистый хелпер `labelFor(refs, field, value)` в `audit/domain/` — покрывается
  `node --test` рядом с `diff.ts`, без jsdom.
- `diff-view.tsx`: `render()` спрашивает хелпер. Скаляр рисуется как
  `Редактор ·9b75ebfc`: подпись, затем укороченный идентификатор — первые 8
  символов у uuid, целиком у числового (`pump-01 ·7`), потому что резать `7`
  не от чего. Массив рисуется поэлементно. Без подписи выводится голое
  значение, как сейчас.
- `diff.ts` не трогается: сравнение снимков от подписей не зависит.

## Тесты

- Go, `gateway/internal/service/audit_refs_test.go`: табличный тест на сбор
  ссылок из снимка (включая массив, сломанный JSON, сущность без ссылок) и на
  сборку словаря из ответов резолверов, включая частичный отказ одного из них.
- Go, catalog: тест `ResolveLabels` на неизвестный вид и на пустой запрос.
- Frontend, `node --test`: `labelFor` — попадание, промах, массив, значение
  `null`.

## Что осознанно не делаем

- **Подпись записи для связующих таблиц.** У `user_role` останется пустой
  `entityLabel`; смысл записи живёт в diff. Сделать заголовком
  «ivan.petrov → Редактор» можно, но это правка миграции с триггерами —
  отдельная задача.
- **Подписи в CSV** — там нет снимков.
- **Кеш ролей и прав в gateway** — два мелких вызова на страницу. Добавить,
  когда померяем, а не заранее.
- **Ссылки-переходы с подписей** — `entity-link.tsx` уже решает, что кликабельно;
  расширять его на поля внутри diff в этой задаче не требуется.

## Порядок работ

1. proto: `ResolveLabels` + `make proto-gen`.
2. catalog: хранилище и сервис `ResolveLabels`.
3. gateway: клиент catalog, таблица полей, `resolveRowRefs`, флаг `wantRefs`.
4. openapi: `refs` в `AuditPage` + `make openapi-gen`.
5. frontend: `yarn openapi:generate`, гейтвей, хук, `labelFor`, `diff-view`.
