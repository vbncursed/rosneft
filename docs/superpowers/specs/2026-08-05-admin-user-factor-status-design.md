# Статус факторов (2FA и passkey) в `/admin/users` — дизайн

**Goal:** В `/admin/users` колонка «2FA» показывает «No» для каждого
пользователя независимо от реального состояния. Починить корень, а не колонку, и
добавить рядом колонку «Passkey» (включён / не включён, без количества).

**Контекст:** баг найден заказчиком. Разбор проведён по коду; корень
подтверждён структурно — это не рассинхронизация данных, а поле, которое на
этом маршруте не заполняется никогда.

---

## Часть 1. Почему «2FA» всегда «No»

### Корень

`auth-service` **не владеет** состоянием 2FA и никогда не заполняет
`authv1.User.totp_enabled`. Это сказано прямо в
`auth-service/internal/transport/grpcapi/converters.go:16`:

```go
// totp_enabled is owned by twofa-service; the gateway overlays the real
// value via twofa.IsEnabled when composing the user DTO.
```

Наложение действительно есть — но ровно в одном обработчике шлюза,
`authhttp/account.go:20` (`GET /api/auth/me`). Поэтому `/account` показывает
правду.

Все админские обработчики в `authhttp/users.go` — `listUsers`, `getUser`,
`createUser`, `updateUser`, `freezeUser`, `unfreezeUser`, `restoreUser`,
`setUserOwner` — вызывают голую функцию `userToJSON` (`authhttp/dto.go:39`),
которая читает `u.GetTotpEnabled()`. Это поле всегда `false`.

**Отсюда следствие:** `/admin/users` показывает не устаревшее значение, а
захардкоженное. То же самое возвращают ответы на создание и редактирование
пользователя.

### Почему починка «дописать наложение в listUsers» — неправильная

Это ровно та форма, которая уже подвела в этом репозитории: проверка, которую
надо помнить в каждом вызывающем. Восемь обработчиков строят пользовательский
DTO, наложение забыто во всех восьми. Дописать его в один — оставить семь
сломанными и не помешать девятому появиться таким же.

Лекарство то же, что и в прошлый раз: убрать возможность забыть. Голая функция
`userToJSON` исчезает, вместо неё появляются методы `*Handlers`, у которых есть
доступ к клиентам факторов. Новый админский маршрут не сможет отдать
пользователя мимо наложения, потому что отдавать будет нечем.

---

## Часть 2. Статуса passkey сегодня нет вообще

`PasskeyService.ListCredentials` аутентифицирован **токеном** и резолвит
вызывающего через `auth.GetMe` (`passkey.proto:36`). Спросить «есть ли passkey у
пользователя X» невозможно ни одним существующим RPC. Новый RPC неизбежен.

---

## Часть 3. Решение

### 3.1. Пакетные RPC во внутренней поверхности обоих сервисов

Раз новый RPC для passkey всё равно нужен, обе выборки делаются пакетными.
Список админки — это N пользователей; поштучные вызовы дали бы 2N round trip на
одну загрузку страницы, пакетные дают два.

```proto
// twofa.proto — internal surface, рядом с IsEnabled
rpc EnabledFor(EnabledForRequest) returns (EnabledForResponse);
message EnabledForRequest  { repeated string user_ids = 1; }
message EnabledForResponse { repeated string enabled_user_ids = 1; }

// passkey.proto — новая internal surface
rpc CredentialedUsers(CredentialedUsersRequest) returns (CredentialedUsersResponse);
message CredentialedUsersRequest  { repeated string user_ids = 1; }
message CredentialedUsersResponse { repeated string user_ids_with_credentials = 1; }
```

Ответ — список включённых, а не `map<string,bool>`: отсутствие id в ответе и
есть «выключено», отдельного значения для этого не нужно.

Существующий `IsEnabled` **не трогается** — на нём висит путь логина в
`auth-service` и step-up в `passkey.go:93`.

Хранилища: один запрос каждое.

```sql
-- twofa_credentials
SELECT user_id FROM twofa_credentials WHERE user_id = ANY($1) AND enabled
-- passkey_credentials
SELECT DISTINCT user_id FROM passkey_credentials WHERE user_id = ANY($1)
```

Пустой вход — пустой выход без похода в базу.

### 3.2. Безопасность новых RPC

Оба лежат во внутренней поверхности (без токена), тем же уровнем, что
`IsEnabled` и `Verify`: сеть между сервисами уже является границей доверия.

Шлюз зовёт их только из маршрутов, уже закрытых `users:read`, и передаёт
**только те id, которые вернул `auth.ListUsers`** — то есть выборку, уже
суженную арендатором и грантами вызывающего. Произвольный id в запрос попасть не
может: он не приходит из query string и не приходит из тела.

Ответ не раскрывает ничего сверх булева факта «фактор настроен». Ни секрет, ни
количество ключей, ни их имена внутренней поверхностью не отдаются.

### 3.3. Наложение — одно место на весь админский срез

`userToJSON` перестаёт быть свободной функцией и становится парой методов:

```go
func (h *Handlers) userJSON(ctx context.Context, u *authv1.User) userJSON
func (h *Handlers) usersJSON(ctx context.Context, in []*authv1.User) []userJSON
```

Внутри — один вызов `h.factors(ctx, ids...)`, который делает оба пакетных RPC
(параллельно, `errgroup`) и возвращает два множества.

Все восемь обработчиков `users.go` переходят на них — по одной строке в каждом.

### 3.4. Недоступность сервиса факторов: `null`, а не `false` и не ошибка

Оба поля в DTO становятся указателями:

```go
TOTPEnabled    *bool `json:"totpEnabled,omitempty"`
PasskeyEnabled *bool `json:"passkeyEnabled,omitempty"`
```

`nil` = «неизвестно», поле выпадает из JSON, таблица рисует «—».

Ошибка RPC даёт `nil`, а не проваленный запрос. Это одно правило на весь код —
благодаря ему в шлюзе не появляется ветки «на этом маршруте падаем, на том
глотаем»:

- админские маршруты остаются доступными при упавшем twofa/passkey и **не
  показывают статуса, который не смогли проверить** — это и есть починка
  исходного бага, а не его новая форма;
- `GET /api/auth/me` остаётся на пути загрузки SPA и не имеет права падать;
  прежнее «проглотить ошибку» становится частным случаем общего правила, а не
  исключением из него.

Ошибка при этом логируется на `warn` — молчаливое «—» должно быть
диагностируемым.

### 3.5. `/api/auth/me` не запрашивает статус passkey

`me` зовётся на каждой загрузке страницы. Наложение passkey туда не идёт:
потребителя нет — `passkeys-section.tsx` тянет учётные данные напрямую своим
маршрутом. `passkeyEnabled` в ответе `/me` отсутствует (`null`), лишнего RPC на
горячем пути не появляется.

Наложение 2FA в `me` остаётся как есть — одиночный `IsEnabled`, который там уже
вызывается.

## Часть 4. Фронтенд

### Контракт

`openapi.yaml`, схема `AuthUser`:

```yaml
totpEnabled:    { type: boolean, description: "absent = состояние неизвестно (сервис 2FA недоступен)" }
passkeyEnabled: { type: boolean, description: "у пользователя есть хотя бы один passkey; absent = неизвестно" }
```

Затем `yarn openapi:generate` (dto.ts) и `make -C backend openapi-gen`
(`openapi_gen.go`).

### Домен

`Principal.totpEnabled` становится `boolean | null`, добавляется
`passkeyEnabled: boolean | null`. `mapPrincipal` — `d.totpEnabled ?? null`.

Потребители после смены типа:

| место | было | станет |
| --- | --- | --- |
| `routes/account.tsx:26` | `initiallyEnabled={p.totpEnabled}` | `p.totpEnabled ?? false` |
| `passkeys-section.tsx:59` | `me?.totpEnabled ?? false` | без изменений |
| `user-row.tsx:58` | тернарник Yes/No | `FactorPill` |

`account.tsx` при неизвестном состоянии деградирует до «2FA не включена». Это
**осознанное ограничение, а не недосмотр**: `/account` управляет собственным
фактором пользователя, и при упавшем twofa-service любая кнопка там всё равно не
сработает. Тристейт на этой странице — отдельная задача, в этот объём не входит.

### Таблица

- `users-table.tsx`: `<th>Passkey</th>` после «2FA», `colSpan` 6 → 7, `min-w`
  `46rem` → `52rem` (седьмая колонка на телефоне без этого доламывает вёрстку —
  контейнер уже `overflow-x-auto`, ширину надо просто дать).
- `user-row.tsx`: тернарник 2FA вынимается в локальный `FactorPill` и
  используется дважды. Три состояния: `true` → «Yes» (emerald), `false` → «No»
  (red), `null` → «—» (neutral, `title="Status unavailable"` — интерфейс
  англоязычный, как и остальные подписи в таблице).

Оба файла остаются заметно ниже потолка в 200 строк.

## Часть 5. Проверки

| уровень | проверка |
| --- | --- |
| twofa, service | `EnabledFor` на минимок-сторе: возвращает только включённых; незаписанный id отсутствует в ответе; пустой вход не ходит в стор |
| passkey, service | `CredentialedUsers` там же: пользователь без ключей отсутствует в ответе; пользователь с двумя ключами присутствует один раз |
| gateway, `dto_test.go` | чистые конвертеры: флаг берётся из множества, а не из proto; `nil`-множество даёт отсутствующий ключ, а известное `false` — присутствующий |
| gateway, `factors_test.go` | клиенты факторов на мёртвом порту: недоступный сервис даёт «неизвестно», а не «выключено»; `me` не ходит за passkey |
| frontend, vitest | `user-row.spec.tsx`: три состояния каждой из двух колонок |

Маршрутного теста на `listUsers` нет намеренно: `Handlers.client` — конкретный
`*auth.Client`, успешный ответ auth-service в юните не подделать без интерфейса,
заведённого ради теста, и существующий `handlers_test.go` по той же причине
покрывает только пути отказа. Решение вынесено в чистую функцию — по конвенции
репозитория, — и покрыто там; то, что обработчики зовут именно её, обеспечено
компилятором: конвертера без множеств больше не существует.

Мок-стор `Store` в обоих сервисах генерируется minimock (`//go:generate`) —
после расширения интерфейса моки перегенерируются, не правятся руками.

Перед коммитом — `make -C backend check`.

## Что сознательно не делается

- **Количество passkey** — заказчик просил бинарный статус; число админу ничего
  не решает и требует отдельной колонки ширины.
- **Тристейт на `/account`** — см. «Часть 4 → Домен».
- **Кэширование выборки факторов** — список админки открывают редко, два
  локальных gRPC на загрузку не являются проблемой. Мерить прежде, чем кэшировать.
- **Фильтр/сортировка по новым колонкам** — не запрошено.
