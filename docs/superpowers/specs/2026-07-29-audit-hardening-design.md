# Журнал изменений: доказуемость и видимость — дизайн

Дата: 2026-07-29
Статус: утверждён, готов к планированию реализации
Предшественник: [`2026-07-28-audit-log-design.md`](2026-07-28-audit-log-design.md)

## Задача

Аудит функциональности от 2026-07-29 оценил журнал изменений в ~90% готовности
и назвал четыре пробела. Задача — закрыть их. Внешнего драйвера (требования ИБ,
комплаенса, жалобы пользователей) нет, поэтому объём определяется инженерной
целесообразностью: то, что не окупается, отбрасывается явно и с обоснованием.

## Переоценка пробелов

Три из четырёх пробелов были **осознанными решениями** исходной спеки, а не
недоделками. Проверка кода изменила формулировку ещё двух.

| Пробел из аудита | Что выяснилось | Решение |
| --- | --- | --- |
| Артефакты конверсии не аудируются | `UpsertTerritory` идёт через `audittx.Run` (`catalog-service/internal/storage/upsert_territory.go:33`), поэтому замена исходника территории попадает в журнал как изменение `source_blob_hash`. Человеческое намерение зафиксировано; не пишется только регистрация артефактов воркером — запись без актора | **Работы нет.** Абзац в README audit-service |
| Нет hash-chain | Цепочка, лежащая в той же базе, не защищает от единственного противника, ради которого её строят: кто может уронить триггер, тот может и пересчитать цепочку. Ценность появляется только при свидетельстве вне базы | **Переформулировано**: периодические дайджесты + свидетельство в файл на отдельном томе |
| Нет ретенции | Удалить старое, не сломав append-only, можно только партиционированием (`DROP PARTITION` — DDL, строковый триггер его не видит). Переезд перетряхивает самую сильную гарантию системы ради проблемы, объём которой не измерен | **Переформулировано**: метрика + алерт + инструмент экспорта. Партиционирование — записанный путь апгрейда |
| Журнал видят только Root и Company Owner | Механика фильтра по актору уже есть в `domain.Filter.ActorID`; расширение скоупа — небольшая правка одной чистой функции | **Делаем**: право `audit:read_own` |

## Решения

| Вопрос | Решение |
| --- | --- |
| Доказуемость неизменяемости | Периодические контрольные дайджесты, сцепленные между собой |
| Где считается дайджест | Целиком в SQL через `pgcrypto`; строки не ездят в Go |
| Свидетельство | Строка в лог сервиса **и** строка JSONL в append-only файл на отдельном томе |
| Внешний приёмник дайджестов | Не делаем; лог-строка с устойчивым ключом готова к нему без правок кода |
| Хеш в каждой строке `audit_log` | Не делаем — не добавляет к дайджесту диапазона, но трогает `audit_capture()` |
| Блокировка на пути записи | Нет. Чекпоинтер не касается пути мутаций вообще |
| Проверка | Подкоманда CLI `audit verify`, не gRPC. Proto не меняется |
| Видимость своих действий | Право `audit:read_own` ролям `editor` и `viewer` |
| CSV-экспорт для `read_own` | Нет, остаётся на `audit:read` |
| Ретенция | Хранить бессрочно; метрика + алерт + `audit export`. Автоудаления нет |
| Партиционирование | Не сейчас; записано как путь апгрейда по срабатыванию алерта |
| Аудит артефактов конверсии | Не делаем |

## Архитектура

### 1. Таблица чекпоинтов

Миграция audit-service `00004_checkpoints.sql`:

```sql
CREATE TABLE audit_checkpoint (
    id          BIGSERIAL PRIMARY KEY,
    at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    from_id     BIGINT NOT NULL,  -- исключительно
    to_id       BIGINT NOT NULL,  -- включительно
    watermark   BIGINT NOT NULL,  -- last_value последовательности на момент тика
    row_count   INT    NOT NULL,  -- не `rows`: ключевое слово PostgreSQL
    digest      TEXT   NOT NULL,  -- hex sha256
    prev_digest TEXT   NOT NULL   -- дайджест предыдущего чекпоинта; '' у затравки
);

CREATE TRIGGER audit_checkpoint_no_mutate BEFORE UPDATE OR DELETE ON audit_checkpoint
    FOR EACH STATEMENT EXECUTE FUNCTION audit_immutable();
CREATE TRIGGER audit_checkpoint_no_truncate BEFORE TRUNCATE ON audit_checkpoint
    FOR EACH STATEMENT EXECUTE FUNCTION audit_immutable();
REVOKE UPDATE, DELETE, TRUNCATE ON audit_checkpoint FROM PUBLIC;
```

`audit_immutable()` существует с миграции `00001` — переиспользуется, не пишется
заново. Сцепка через `prev_digest` означает, что подмена одного чекпоинта требует
пересчёта всех последующих.

### 2. Как считается дайджест

```sql
SET LOCAL timezone = 'UTC';
SELECT count(*),
       coalesce(max(l.id), $from),
       encode(digest($prev || coalesce(string_agg(to_jsonb(l.*)::text, E'\n' ORDER BY l.id), ''),
                     'sha256'), 'hex')
FROM audit_log l
WHERE l.id > $from AND l.id <= $boundary;
```

- `pgcrypto` уже установлено в базе `andrey` (auth-миграция `00001`) — новых
  зависимостей нет.
- `to_jsonb(l.*)` даёт канонический вид: jsonb сортирует ключи, поэтому порядок
  колонок в таблице на результат не влияет.
- `SET LOCAL timezone = 'UTC'` обязателен: без него jsonb отрендерит `timestamptz`
  в таймзоне сессии, и дайджест перестанет воспроизводиться на машине с другой
  `TZ`. Контейнеры проекта работают в `Europe/Moscow`, так что расхождение
  наступило бы сразу.
- Пустой диапазон даёт `count = 0` и дайджест от одного `$prev` — чекпоинт всё
  равно пишется, цепочка не рвётся.

### 3. Граница диапазона: почему не `max(id)`

Наивная граница даёт ложные тревоги. Транзакция A получает `id = 100` и держит;
транзакция B получает `id = 101` и коммитится; тик считает дайджест до 101, не
видя невидимую сотую; A коммитится — и в уже покрытом диапазоне появляется строка.
`verify` сообщит о подделке там, где её нет.

Невидимую строку нельзя увидеть по определению, поэтому граница берётся не из
таблицы, а из последовательности — она выдаёт `id` **до** коммита:

```
boundary = watermark предыдущего чекпоинта
w        = pg_sequence_last_value('audit_log_id_seq')   -- снимаем сейчас, для следующего тика
digest   = свёртка по (prev.to_id, boundary]
INSERT audit_checkpoint {from_id: prev.to_id, to_id: max(id) в диапазоне,
                         watermark: w, row_count, digest, prev_digest: prev.digest}
```

Диапазоны смежны: `from_id` следующего равен `to_id` предыдущего, поэтому в
покрытии не бывает дыр. `to_id` берётся как `max(id)` внутри диапазона, а не как
сама граница: за границей по определению ничего не появится, а более короткий
диапазон дешевле пересчитывать.

`watermark`, снятый на прошлом тике, — рубеж, за которым все идентификаторы уже
розданы. К моменту текущего тика каждая транзакция, живая на прошлом,
завершилась коммитом или откатом. Откаты оставляют постоянные дыры в
нумерации — это не мешает, дайджест считается по существующим строкам, а дыры
стабильны.

Первый запуск пишет затравку `{from_id: 0, to_id: 0, watermark: w, row_count: 0,
digest: sha256(""), prev_digest: ''}` и ничего не считает. Значение хранится в
таблице, а не в памяти, поэтому перезапуск сервиса ничего не ломает.

**Потолок (`ponytail:`)**: интервал тика обязан превышать время жизни самой
длинной пишущей транзакции. Мутации в этой системе односоставные, дефолт `5m`
взят с большим запасом. Транзакция, живущая дольше, даёт **ложную тревогу**
`verify`, а не пропуск подделки — отказ в безопасную сторону. Путь апгрейда:
брать границу из `pg_snapshot_xmin(pg_current_snapshot())`, если когда-нибудь
появятся долгие пишущие транзакции.

### 4. Свидетельство

Две записи на каждый чекпоинт.

**Лог сервиса** — строка с устойчивым ключом, чтобы будущий сборщик логов ловил
её grep'ом без правок кода:

```go
logger.Info("audit: checkpoint", "from_id", …, "to_id", …, "row_count", …, "digest", …)
```

**Файл** — JSONL на отдельном томе:

```
{"at":"2026-07-29T10:15:00Z","from_id":4120,"to_id":4187,"row_count":67,"digest":"9f2c…","prev_digest":"41ab…"}
```

- Путь — `AUDIT_DIGEST_FILE`, дефолт пустой (выключено). Compose выставляет
  `/var/audit/digests.jsonl`; локальный `./bin/audit serve` без каталога не падает.
- Файл открывается один раз при старте (`O_APPEND|O_CREATE|O_WRONLY`, `0600`),
  после каждой записи — `Sync()`. Одна строка в 5 минут: fsync здесь бесплатен и
  ровно в этом смысл.
- Порядок операций: посчитать дайджест → вставить строку чекпоинта → дописать
  файл → залогировать. Сбой записи в файл **не откатывает** чекпоинт: цепочка в
  базе остаётся целой, а пробел в свидетельстве обнаруживается сам. Сбой уходит в
  `ERROR` и в счётчик `audit_digest_write_failures_total`, на него — правило
  Prometheus.
- Том `audit-digest` в compose, отдельный от тома базы. Смысл именно в раздельном
  бэкапе: дамп базы и файл свидетельств должны уезжать разными путями.
- **Ловушка с правами на том**: distroless-сервис работает как `nonroot` и не
  запишет в корень свежесозданного тома. Каталог `/var/audit` предсоздаётся в
  Dockerfile как `nonroot:nonroot`, том инициализируется из него — тот же приём,
  что уже применён к `blob-data` в mesh-worker.
- Ротация не нужна: ~100 КБ в год.

### 5. Проверка

Подкоманда `audit verify` (сверка с файлом — по уже существующему `--digest-file` / `AUDIT_DIGEST_FILE`):

1. Идёт по `audit_checkpoint` по возрастанию `id`.
2. Пересчитывает дайджест каждого чекпоинта по его же диапазону и `prev_digest`.
3. Сверяет сцепку: `prev_digest` каждого равен `digest` предыдущего.
4. При заданном `--digest-file` сверяет каждый чекпоинт со строкой файла по `to_id`;
   отсутствие строки — предупреждение, расхождение дайджеста — ошибка.
5. Печатает первое расхождение с диапазоном и завершается с кодом ≠ 0.

Файл — это то, что делает проверку осмысленной. Без него `verify` ловит
небрежную подделку (правку строк без пересчёта цепочки); с ним — аккуратную,
потому что переписать историю, пересчитать цепочку в базе и синхронно подменить
файл на другом томе заметно труднее.

### 6. Размещение тика

`bootstrap.RunServe` уже поднимает горутины под метрики и gRPC. Чекпоинтер встаёт
третьей, после `EnsureTriggers`. Останавливается по `rootCtx`, вместе со всем
остальным. Тик, совпавший с завершением работы, дописывается или отменяется
целиком — чекпоинт пишется одной транзакцией.

## Право `audit:read_own`

Миграция auth `00013_audit_read_own.sql`: новое право + грант ролям `editor` и
`viewer`. Роль `guest` не получает — гость почти не совершает действий.

`AuditScope` возвращает структуру вместо трёх значений:

```go
type AuditScope struct { All bool; Company, Actor string }

Root                → {All: true}
есть audit:read     → {Company: c}
есть audit:read_own → {Company: c, Actor: self}
иначе               → ErrForbidden
```

Актор в режиме `read_own` **перезаписывает** параметр запроса, а не дополняет:
иначе фильтром `?actor=` можно было бы выйти за свой скоуп. Компания ставится и
здесь, хотя пиннинг по актору строго уже — две проверки дешевле одного
рассуждения о том, почему хватает одной.

Гейт маршрута: значение `routePerms` становится **списком** прав, проверка —
«есть любое из». Обе записи `/api/audit` получают
`{"audit:read", "audit:read_own"}`, сужение до своих действий делает `AuditScope`.

Убирать записи из карты нельзя: `RequirePermissionForRoute` **fails open** —
маршрут, отсутствующий в карте, проходит с любой сессией
(`route_permissions_test.go:16` предупреждает об этом прямым текстом и стережёт
именно эти два маршрута). Список прав сохраняет предохранитель, а существующему
тесту меняет только ожидание.

`/api/audit.csv` остаётся на `audit:read`: экспорт всей истории компании не для
рядового пользователя.

Фронт: секция «Мои действия» в `/account`, рядом с passkeys и 2FA. Переиспользует
готовую `<AuditPanel>` с зафиксированным фильтром и скрытым выбором актора.

## Ретенция

Ничего не удаляем — даём знать, когда станет пора, и чем архивировать.

- Два gauge на том же тике, что и чекпоинт: `audit_log_rows` и `audit_log_bytes`
  (через `pg_total_relation_size`). Тик уже ходит в базу, отдельного расписания не
  нужно.
- Правило в `ops/prometheus/rules.yml`: `audit_log_bytes > 5e9` в течение часа →
  `severity: warning`.
- Подкоманда `audit export --before=DATE --out=FILE.jsonl` — потоковый экспорт,
  ничего не удаляет.
- README audit-service: политика хранения — бессрочно, пересмотр по срабатыванию
  алерта; партиционирование описано как путь апгрейда с обоснованием, почему
  сейчас не делается.

## Тесты

Интеграционные (testcontainers, build-тег `integration`, рядом с существующими в
`internal/migrate/`):

- чекпоинт покрывает свой диапазон; повторный тик не дублирует и не пропускает строки;
- пустой интервал даёт чекпоинт с `row_count = 0` и не рвёт цепочку;
- `verify` ловит подмену строки (`DROP TRIGGER` → `UPDATE` → пересоздать);
- `verify` ловит удаление строки;
- `verify` ловит подмену чекпоинта через разрыв `prev_digest`;
- `verify --digest-file` ловит расхождение базы с файлом;
- транзакция, открытая до тика и закоммиченная после, не даёт ложной тревоги
  (проверка механики watermark);
- триггеры неизменяемости на `audit_checkpoint` отбивают `UPDATE`, `DELETE`, `TRUNCATE`.

Юнит:

- три режима `AuditScope` + отказ;
- перезапись `ActorID` в режиме `read_own` не поддаётся параметру `?actor=`;
- сериализация строки JSONL;
- экспорт JSONL.

Фронт: spec на секцию «Мои действия» в `/account`.

## Чего не делаем

Записано явно, чтобы следующий аудит не назвал это пробелом повторно:

- **Партиционирование `audit_log`** — единственный способ реально удалять
  историю, не ломая append-only, но переезд трогает самую надёжную часть системы
  ради неизмеренной проблемы. Триггер — срабатывание алерта на размер.
- **Автоматическое удаление или архивация по расписанию** — политика «хранить
  бессрочно» осознанна.
- **Хеш в каждой строке `audit_log`** — не добавляет ничего к дайджесту
  диапазона, но требует правки `audit_capture()`, самой критичной функции схемы.
- **Отправка дайджестов во внешний сервис** (S3, webhook) — тянет зависимость,
  конфиг доступов и обработку недоступности приёмника. Лог-строка и файл готовы к
  тому, чтобы это надстроить позже.
- **Аудит артефактов конверсии** — записи без человеческого актора; намерение уже
  зафиксировано через `territories.source_blob_hash`.
- **gRPC-метод для verify** — это операционный инструмент, не пользовательская
  функция. Proto не меняется.
